# `existingRows` is sourced from the Sheet, and idempotency hashes the merged row, not just Adapter-Owned fields

Manual end-to-end testing ([#21](https://github.com/vampifi/novo-furniture-store/issues/21)) found that editing a Business-Owned field (e.g. Retail Price) directly in a Supplier Tab never reached Medusa on the next cycle. Two previously-undecided or incorrectly-assumed design points caused this together.

**Where `existingRows` comes from.** No real `SupplierTabIO` implementation exists yet (spec §11, deferred), so this was never pinned down concretely. We decided `existingRows.product` is read from **the Sheet's current state** — not Medusa's last-known state. This is what lets a business owner's in-sheet edit ever be visible to reconciliation at all; sourcing it from Medusa (as an early test harness incorrectly did) means the merge step preserves Medusa's *old* business-owned values instead of the Sheet's *current* ones, silently discarding the edit it was supposed to preserve. The hash associated with a row still lives in `variant.metadata` (no new storage introduced) — only the product data itself moves to the Sheet as its source.

**What triggers a sync.** Fixing the sourcing above isn't sufficient on its own: the existing idempotency check (`hashAdapterOwnedFields`) only ever hashes `fresh` (the Adapter's output) and compares it to the stored hash — it never inspects `existingRows.product` for the skip decision, so a Business-Owned-only edit still produces an identical hash and is still skipped. We decided to hash the **merged row** (the actual `mergeProduct(existing, fresh)` result — Adapter-Owned fields from `fresh`, Business-Owned fields from the Sheet's current `existing.product`) as a single whole-row fingerprint, computed *after* merging rather than over `fresh` in isolation, replacing `hashAdapterOwnedFields`. One hash, checked against four scenarios (nothing changed; only Adapter-Owned changed; only Business-Owned changed; both changed in the same cycle gap) — all four resolve correctly with this single check, with no need for a second hash.

## Considered Options

- **Two separate hashes** (one over Adapter-Owned fields only, to gate whether a refresh is needed; a second over the whole row, to gate whether Medusa needs an update) — rejected as unnecessary complexity once merge-then-hash was worked through: the single whole-row hash, computed after merging, already handles every scenario a second hash would have been introduced to cover.
